# Harness Engineering: Leveraging Codex in an Agent-First World (OpenAI)

> [!tldr] In a five-month experiment (first commit late Aug 2025 → early 2026), an OpenAI team built and shipped an internal beta product with **zero lines of manually-written code**: application logic, tests, CI configuration, documentation, observability, and internal tooling were all written by Codex agents. The post distills the harness-engineering lessons: engineers stop writing code and instead design environments, specify intent, and build feedback loops ("Humans steer. Agents execute."); repository knowledge becomes the system of record (a ~100-line AGENTS.md as table of contents, not encyclopedia); the codebase is optimized for agent legibility; architecture is enforced mechanically via invariants rather than micromanagement; and agent-generated drift is handled by recurring "garbage collection" tasks. The team estimates ~1/10th the hand-written time, ~1 million lines across ~1,500 PRs.

**Author:** Ryan Lopopolo, Member of the Technical Staff, OpenAI · **Published:** 2026-02-11 · **URL:** https://openai.com/index/harness-engineering/ · **Acknowledgements:** Victor Zhu, Zach Brock, and the team that built the product ^[extracted]

## Overview

OpenAI's first-party account of running a software team whose primary job is no longer writing code but designing environments, specifying intent, and building feedback loops that let Codex agents do reliable work. The constraint was chosen deliberately — "no manually-written code" — to force the team to build what was necessary to increase engineering velocity by orders of magnitude, with human time and attention as the scarce resource. The product shipped, deploys, breaks, and gets fixed, with internal daily users and external alpha testers. ^[extracted]

## Key Points

### We started with an empty git repository

The first commit landed late August 2025. The initial scaffold (repository structure, CI, formatting rules, package manager setup, application framework) was generated by Codex CLI using GPT‑5, guided by a small set of existing templates — even the initial AGENTS.md was written by Codex. There was no pre-existing human-written code anchoring the system. ^[extracted]

Five months later the repository holds on the order of a million lines of code, with roughly 1,500 pull requests opened and merged by a small team of three engineers driving Codex — an average of 3.5 PRs per engineer per day, with throughput **increasing** as the team grew to seven. The product has been used by hundreds of users internally, including daily power users. ^[extracted]

### Redefining the role of the engineer

Early progress was slower than expected not because Codex was incapable but because the environment was underspecified. The team worked depth-first: breaking larger goals into smaller building blocks (design, code, review, test) and using them to unlock more complex tasks. When something failed, the fix was almost never "try harder" — the question became "what capability is missing, and how do we make it both legible and enforceable for the agent?" ^[extracted]

Humans interact with the system almost entirely through prompts. To drive a PR to completion, Codex reviews its own changes locally, requests additional agent reviews locally and in the cloud, responds to feedback, and iterates until all agent reviewers are satisfied — a loop the post calls a Ralph Wiggum Loop. Over time nearly all review effort moved agent-to-agent; humans may review PRs but aren't required to. ^[extracted]

### Increasing application legibility

With throughput up, the bottleneck became human QA capacity, so the team made the application itself legible to Codex: the app is bootable per git worktree (one instance per change), the Chrome DevTools Protocol is wired into the agent runtime, and skills cover DOM snapshots, screenshots, and navigation — letting Codex reproduce bugs, validate fixes, and reason about UI behavior. Observability was made ephemeral per worktree too: agents query logs with LogQL and metrics with PromQL, making prompts like "ensure service startup completes in under 800ms" tractable. Single Codex runs regularly work on one task for upwards of six hours, often while the humans sleep. ^[extracted]

### We made repository knowledge the system of record

The core lesson: **give Codex a map, not a 1,000-page instruction manual.** The team tried the "one big AGENTS.md" approach and it failed in predictable ways: context is a scarce resource (a giant file crowds out the task); too much guidance becomes non-guidance (when everything is "important," agents pattern-match locally); it rots instantly (a graveyard of stale rules); and it is hard to verify mechanically. ^[extracted]

Instead, AGENTS.md (roughly 100 lines) is injected into context as the **table of contents**, while the repository's knowledge base lives in a structured `docs/` directory treated as the system of record: design docs with verification status and core beliefs, `ARCHITECTURE.md` as a top-level map, first-class execution plans with progress/decision logs, product specs, `*-llms.txt` references, and per-domain quality grades. This enables **progressive disclosure** — agents start from a small stable entry point and are taught where to look next. It is enforced mechanically: dedicated linters and CI jobs validate that the knowledge base is up to date and cross-linked, and a recurring "doc-gardening" agent scans for stale docs and opens fix-up pull requests. ^[extracted]

### Agent legibility is the goal

Because the repository is entirely agent-generated, it is optimized first for Codex's legibility: from the agent's point of view, anything it can't access in-context while running effectively doesn't exist — knowledge in Google Docs, chat threads, or people's heads is inaccessible. The team pushed more and more context into the repo over time, treating agent onboarding like human onboarding (product principles, engineering norms, emoji preferences included). ^[extracted]

This framing clarified tradeoffs: they favored dependencies and abstractions that could be fully internalized and reasoned about in-repo. "Boring" technologies are easier for agents to model due to composability, API stability, and representation in the training set; in some cases it was cheaper to have the agent reimplement subsets of functionality than work around opaque upstream behavior (e.g. a custom map-with-concurrency helper instead of a p-limit-style package, integrated with OpenTelemetry and 100% test-covered). Pulling more of the system into a form agents can inspect, validate, and modify directly increases leverage — for Codex and for other agents working on the codebase, e.g. Aardvark. ^[extracted]

### Enforcing architecture and taste

Documentation alone doesn't keep a fully agent-generated codebase coherent: the team enforces **invariants, not implementations**. They require Codex to parse data shapes at the boundary (without prescribing the library — "the model seems to like Zod"), and built the application around a rigid architectural model: each business domain is divided into a fixed set of layers (Types → Config → Repo → Service → Runtime → UI) with strictly validated dependency directions, and cross-cutting concerns (auth, connectors, telemetry, feature flags) enter only through a single explicit interface — Providers. Custom linters (Codex-generated) and structural tests enforce the rules, plus "taste invariants" like structured logging, schema/type naming conventions, and file size limits; lint error messages are written to inject remediation instructions into agent context. This is "enforce boundaries centrally, allow autonomy locally" — the kind of architecture usually postponed until you have hundreds of engineers, but with agents it becomes an early prerequisite. ^[extracted]

Human taste is fed back continuously: review comments, refactoring PRs, and user-facing bugs are captured as documentation updates or encoded directly into tooling; when documentation falls short, the rule is promoted into code. ^[extracted]

### Throughput changes the merge philosophy

As Codex's throughput increased, conventional norms became counterproductive: the repository runs minimal blocking merge gates, PRs are short-lived, and test flakes are addressed with follow-up runs rather than blocking progress. In a system where agent throughput far exceeds human attention, corrections are cheap and waiting is expensive — a tradeoff the authors note would be irresponsible in a low-throughput environment. ^[extracted]

### What "agent-generated" actually means

"Everything in the codebase" — agents produce product code and tests, CI configuration and release tooling, internal developer tools, documentation and design history, evaluation harnesses, review comments and responses, repository-management scripts, and production dashboard definition files. Humans remain in the loop but at a different layer: prioritizing work, translating user feedback into acceptance criteria, and validating outcomes. When the agent struggles, the team identifies what's missing (tools, guardrails, documentation) and feeds it back into the repository — always by having Codex write the fix. Agents use standard development tools directly (gh, local scripts, repository-embedded skills) and often squash and merge their own PRs. ^[extracted]

### Increasing levels of autonomy

As testing, validation, review, feedback handling, and recovery were encoded into the system, the repository crossed a threshold where Codex can end-to-end drive a new feature from a single prompt: validate the codebase state, reproduce the reported bug, record a video of the failure, implement the fix, validate it by driving the application, record a resolution video, open a PR, respond to agent and human feedback, detect and remediate build failures, escalate to a human only when judgment is required, and merge. The post is explicit that this depends heavily on the repository's specific structure and tooling and should not be assumed to generalize without similar investment — at least not yet. ^[extracted]

### Entropy and garbage collection

Full agent autonomy introduces novel problems: Codex replicates patterns that already exist in the repository — even uneven or suboptimal ones — so drift is inevitable. Humans initially spent every Friday (20% of the week) cleaning up "AI slop," which didn't scale. The team instead encoded "golden principles" into the repository (e.g. prefer shared utility packages over hand-rolled helpers to keep invariants centralized; don't probe data "YOLO-style" — validate boundaries or rely on typed SDKs) and built a recurring cleanup process: background Codex tasks scan for deviations, update quality grades, and open targeted refactoring PRs, most reviewable in under a minute and automerged. The post frames this as garbage collection — technical debt as a high-interest loan, better paid down continuously in small increments than compounded. ^[extracted]

### What we're still learning

The strategy has worked up through internal launch and adoption at OpenAI. Open questions the authors flag: how architectural coherence evolves over **years** in a fully agent-generated system; where human judgment adds the most leverage and how to encode that judgment so it compounds; and how the system evolves as models become more capable. What's clear to them: building software still demands discipline, but the discipline shows up in the scaffolding — the tooling, abstractions, and feedback loops — rather than in the code itself. ^[extracted]
