## The Article

Deep dive: [[references/vibecoding-gpu-kernels|Vibecoding GPU Kernels]].

The core claim: handwriting GPU kernels is an **embarrassingly verifiable** task — which is exactly what makes it a good problem for LLM agents (Claude Opus 5, GPT 5.6 Sol) to write and optimize. ^[extracted]

The verifiable loop: ^[extracted]
- **Compile check** — a tight local loop that catches obvious errors before correctness is even considered
- **Correctness check** — the core verifiable-reward loop: compare each kernel version against a slow reference implementation; a fast but wrong kernel is worthless, so correctness is re-verified for every version
- **Optimization** — every new version re-enters the same correctness loop
- **Roofline/satisfaction check** — the outer loop deciding whether to keep optimizing or stop

First version & context: modern LLMs already write good Triton; for lower-level CUDA DSLs (CuTeDSL, Tilelang) a **context directory** helps a lot — e.g. cloning NVIDIA CUTLASS so the agent can look up Layout Algebra, Copy/GEMM atoms, memory hierarchy, and example kernels. ^[extracted]

Validation is the real bottleneck: the reference implementation's speed matters less than its intention, since what you intend to measure and verify is what your agent will optimize for. Metrics: MAE/MSE/RMSE/PSNR for full precision; PSNR and cosine similarity (cossim) for lower precision. Tests are organized as **rungs** — an `@rung` decorator with one test per rung (pre-checks, run, benchmark). ^[extracted]

Benchmark & profile: end-to-end kernel time; intra-kernel tracing (custom tracer or CUPTI); and dumping IR, PTX, SASS, CUBIN to a dumps directory so the agent can read the generated assembly and inline lower-level code over suboptimal DSL output. **NCU (Nsight Compute) profiling** generates a report as part of the verifiable loop. ^[extracted]

Closing: "Is GPU kernel development dead? Well yes but actually no" — yes, because layouts, indexing, and abstractions are largely solved by agents with enough context (2-3 weeks of work → 1-2 days); no, because the bottleneck shifts from kernels to validations, and the human's fundamental GPU understanding plus a good harness — agents as "really smart assistants", not autonomous — is still needed. ^[extracted]
