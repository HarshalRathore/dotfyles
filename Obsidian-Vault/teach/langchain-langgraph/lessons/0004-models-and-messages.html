Models & Messages: The Contract Between Your Code and the Model

In Chapter 3 you traced messages through the loop. In this chapter you learn what those messages are made of, how LangChain talks to any model provider, and how to make the model speak your language back.

You know Pi, the agent coding tool you use every day. Pi has a model inside it. So does Claude Code. So does every agent you have ever used. They all speak to some LLM provider (OpenAI, Anthropic, Ollama, Groq) and they all pass messages back and forth. The provider and the message format change, but the pattern stays the same.

LangChain formalises that pattern into a clean contract. You write Python code; LangChain translates it into provider-specific HTTP calls. You switch providers by changing one string. The model receives typed messages and returns typed messages. Your code never touches a raw API endpoint.

This chapter's win

By the end of this chapter you will have a provider-neutral message lab that works with OpenAI, Anthropic, or a local Ollama model. You will switch providers by changing one line. You will see typed messages flow in and structured data come out. This is the chapter that makes LangChain's abstraction real.

The Provider Boundary

Each LLM provider exposes its own API. The shape of those APIs is similar (messages in, message out) but every detail differs: authentication header, message format, parameter names, error codes, streaming protocol. Writing provider-specific code for each one is exactly the kind of work you should never do.

LangChain draws a line between your code and the provider. Your code talks to a LangChain chat model object. That object talks to the provider behind the scenes. You never construct a raw HTTP request or parse a provider-specific response.

Your Code → ChatModel → Provider API

The piece in the middle is the LangChain chat model interface. It defines one method that matters: invoke. You pass messages in. You get an AIMessage back. Everything else (API key management, retry logic, parameter translation) is handled by the implementation.

Official source

Read the full model interface documentation at docs.langchain.com/oss/python/langchain/models and the provider concepts guide at docs.langchain.com/oss/python/concepts/providers-and-models.

The One Function: init_chat_model

LangChain gives you a single import to create any chat model:

from langchain.chat_models import init_chat_model

model = init_chat_model("openai:gpt-5.5")

response = model.invoke("Hello!")
print(response)
# AIMessage(content='Hello! How can I help you today?', ...)

The "openai:gpt-5.5" string is a provider:model identifier. The part before the colon selects the provider package; the part after selects the model name. LangChain loads the right integration, configures it with your environment credentials, and hands you a ready-to-use object.

Credentials live in the environment

init_chat_model reads credentials from standard environment variables: OPENAI_API_KEY, ANTHROPIC_API_KEY, and so on. Never hardcode keys. Set them in a .env file or your shell profile. The langchain-openai and langchain-anthropic packages handle the rest.

The invoke method accepts either a plain string or a list of message objects. You saw invoke in Chapter 2 inside create_agent; this is the same method, just called directly on the model instead of through the harness.

Official API reference

See the complete init_chat_model signature at reference.langchain.com/python/langchain/chat_models/base/init_chat_model.

model = init_chat_model("openai:gpt-5.5")

model = init_chat_model("anthropic:claude-sonnet-4-6")

Your code stays the same; the model's ability to do what you ask depends on the model, not LangChain. We will return to this caveat in the model parameters section.

Typed Messages, Deeper

Chapter 3 introduced the four message types. Now you will work with them directly in Python. Each type is a class in langchain.messages:

from langchain.messages import (
    SystemMessage,
    HumanMessage,
    AIMessage,
    ToolMessage,
)

Here is what each one carries and when to use it:

ClassConstructor argsUsed when
SystemMessage content: str Setting the model's behaviour at the start of a conversation. Injected once, lasts the whole session.
HumanMessage content: str Wrapping user input. Every turn the user takes becomes a HumanMessage.
AIMessage content: str, tool_calls: list The model's output. Contains text, tool call requests, and metadata like token usage.
ToolMessage content: str, tool_call_id: str Carrying a tool result back to the model. The tool_call_id links it to the specific call that produced it.

You construct them like any Python object:

from langchain.messages import SystemMessage, HumanMessage

messages = [
    SystemMessage("You are a helpful assistant."),
    HumanMessage("What is the capital of Japan?"),
]

response = model.invoke(messages)
print(type(response).__name__)   # AIMessage
print(response.content)          # Tokyo
print(response.tool_calls)       # []  (empty — no tool called)

The model invoke method is polymorphic on input: pass a string, get a reply; pass a list of messages, get a reply. LangChain normalises the string into a HumanMessage internally, but passing explicit typed messages gives you control over the full conversation shape including system prompts.

The message types are serialisable

Every message class can be converted to a dictionary with .dict() or .model_dump() (Pydantic v2) and reconstructed from a dictionary. This is how messages travel across network boundaries and get stored in databases. The canonical schema is documented at docs.langchain.com/oss/python/langchain/messages.

When the model emits an AIMessage with tool calls, the tool_calls field contains structured data that the harness (from Chapter 2) uses to execute your tools:

response = model.invoke("What is the weather in London?")

if response.tool_calls:
    for tc in response.tool_calls:
        print(tc["name"])       # "get_weather"
        print(tc["args"])       # {"location": "London"}
        print(tc["id"])         # "call_abc123"
Connecting to Chapter 3

In Chapter 3 you saw the tool_calls field in the trace. Now you can see it in code: the model returns an AIMessage, and that message carries the tool call requests as structured data. Chapter 5 will teach you how to build tools that receive these calls.

System Prompts

A system prompt is a SystemMessage at the front of your message list. It sets the model's behaviour, tone, and constraints for the entire conversation. Unlike a HumanMessage, the system message is not usually shown to the end user — it is the invisible instruction layer between your code and the model.

from langchain.messages import SystemMessage, HumanMessage

messages = [
    SystemMessage(
        "You are a concise Python tutor. "
        "Answer in five sentences or fewer. "
        "Include a code example when relevant."
    ),
    HumanMessage("What is a decorator?"),
]

response = model.invoke(messages)
print(response.content)

The system prompt is the first message in the list. Provider behaviour varies: some models are sensitive to how the system prompt is phrased — a well-written system prompt can dramatically improve output quality without changing any code.

System prompt vs tool descriptions

The system prompt tells the model how to behave. Tool descriptions (the docstring on your @tool function) tell the model what it can do. They serve different purposes. Do not cram tool descriptions into the system prompt; LangChain sends them separately as part of the tool schema.

When you pass system_prompt to create_agent (as you did in Chapter 2), LangChain adds a SystemMessage at the front of every conversation automatically. Calling model.invoke(messages) directly gives you manual control over that placement.

The Provider-Neutral Message Lab

Here is the practical win for this chapter. Save this as message_lab.py and run it against any provider:

from langchain.chat_models import init_chat_model
from langchain.messages import SystemMessage, HumanMessage, AIMessage

# ── Change this one line to switch providers ──
model = init_chat_model("openai:gpt-5.5")

messages = [
    SystemMessage("You are a concise assistant. Answer in two sentences."),
    HumanMessage("Tell me a fun fact about the Python language."),
]

response = model.invoke(messages)

print(f"Response type:    {type(response).__name__}")
print(f"Content:          {response.content}")
print(f"Tool calls:       {response.tool_calls}")
if response.response_metadata:
    print(f"Model:            {response.response_metadata.get('model', 'N/A')}")
    print(f"Finish reason:    {response.response_metadata.get('finish_reason', 'N/A')}")
if response.usage_metadata:
    print(f"Token usage:      {response.usage_metadata}")

Run it once with OpenAI, then change the init_chat_model string to "anthropic:claude-sonnet-4-6" and run it again. Then try "ollama:llama3.1". The output format is identical. The content will differ (different models give different answers), but the shape is always an AIMessage with content, tool_calls, response_metadata, and usage_metadata (when the provider reports token usage).

What the metadata tells you

usage_metadata provides standardized token usage (input tokens, output tokens, total tokens) when the provider reports it — the keys are the same regardless of provider. response_metadata contains provider-specific information: the exact model name used, finish reason, and any other provider-specific metadata. The keys in response_metadata vary across providers. Both are read-only observability data — you can inspect them but should not build logic that depends on provider-specific keys.

This script is your diagnostic tool for the rest of the course. Whenever you are unsure what a model is doing, drop into the message lab, test your hypothesis with typed messages, and see the raw AIMessage output. No harness, no tools, no graph — just the model contract.

Structured Output: Making the Model Fill in a Form

So far the model has returned free text. But many applications need the model to return structured data: a JSON object with known fields, types, and validation rules. LangChain gives you two ways to achieve this, and understanding the difference between them is important.

Model-level: with_structured_output

The with_structured_output method wraps any chat model and adds output parsing. You give it a Pydantic schema, and the model returns parsed instances of that schema instead of an AIMessage:

from pydantic import BaseModel
from langchain.chat_models import init_chat_model

class MovieReview(BaseModel):
    title: str
    rating: int
    summary: str

model = init_chat_model("openai:gpt-5.5")
structured = model.with_structured_output(MovieReview)

result = structured.invoke(
    "Review the movie Inception."
)
print(f"Title:   {result.title}")
print(f"Rating:  {result.rating}/10")
print(f"Summary: {result.summary}")
# result is a MovieReview instance, not an AIMessage

with_structured_output returns a new model-like object that shares the same invoke interface. When you call invoke, LangChain sends the schema definition to the model along with the messages, tells the model to return JSON matching that schema, and parses the response into your Pydantic class.

Official API reference

See the full with_structured_output signature at reference.langchain.com/python/langchain-core/language_models/chat_models/BaseChatModel/with_structured_output.

Agent-level: response_format

When you use create_agent, you can pass response_format at the agent level:

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[...],
    response_format=MovieReview,
)

The agent-level response_format configures the entire agent loop to produce structured output as its final result. The agent runs its normal loop (model → tools → model → ...) and the final output is parsed into the schema. This is different from with_structured_output, which is a model-level transformation: it replaces the model's output format without involving tools or the agent loop.

# Model level (this chapter)
structured = model.with_structured_output(MovieReview)
result = structured.invoke("Review Inception.")
Replaces the single model call. Returns a MovieReview instance. No harness, no tools, no loop.
# Agent level (Chapter 6)
agent = create_agent(model, tools, response_format=MovieReview)
result = agent.invoke({"messages": [...]})
Wraps the full agent loop. The final output is parsed. Tools can contribute data that feeds the structured result.

The structured output documentation at docs.langchain.com/oss/python/langchain/structured-output covers both modes. For now, focus on with_structured_output: it is the simpler path and the one you will reach for when you need typed data from a single model call.

with_structured_output works best with providers that support native JSON mode or tool-use-based structured output (OpenAI, Anthropic, Google). With Ollama or other local models, the model may return malformed JSON that the parser cannot validate, raising a parsing error. Test structured output with your chosen provider before depending on it.

Predict the Shape

Before you read the next code block, what Python type does structured.invoke(...) return? (The structured variable comes from model.with_structured_output(MovieReview).)

Reveal the answer

It returns a MovieReview instance, not an AIMessage and not a raw string. with_structured_output creates a wrapper that intercepts the model's output, parses the JSON into the Pydantic schema, and returns the validated object. You can access result.title, result.rating, and result.summary directly.

If parsing fails (the model returns invalid JSON), the method raises a parsing error. You can catch it and retry with a different prompt or model.

ParameterWhat it controls
temperature Randomness of the output. 0 = deterministic, 1 = very random. Default varies by provider (usually 0.7 or 1.0).
max_tokens Maximum number of tokens the model can generate in one response. Cuts off output when reached.
timeout Maximum seconds to wait for a response from the provider API. Prevents hanging on a slow request.
max_retries Number of times to retry on transient failures (rate limits, network errors, server errors). Default 6. 
model = init_chat_model(
    "openai:gpt-5.5",
    temperature=0.3,
    max_tokens=500,
    timeout=30,
    max_retries=2,
)

These parameters are standard across providers at the LangChain level. However, each provider may interpret or support them differently — for example, parameter naming, accepted ranges, and additional options like top_p or frequency_penalty vary. Provider capability and behaviour differ; always test your specific provider-model combination.

The LangChain chat model interface gives you a uniform calling convention. It does not give you a uniform capability guarantee. Lower temperature values are generally less random, but the exact behavior varies by provider. Structured output support is provider-dependent; it works on some models and not on others. Tool calling requires a model fine-tuned for it. The interface is the same; the model's capabilities are not. Always test your specific provider-model combination.
