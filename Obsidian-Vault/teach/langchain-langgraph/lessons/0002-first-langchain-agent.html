Your First LangChain Agent

Installing the framework, writing your first create_agent, and seeing exactly what happens at every step of the hidden loop.

If Chapter 1 was the map, this is the first step on the trail.

You now know the mental model: model + tools + loop. You saw the mailroom analogy. You spotted the parts in a code snippet. But you have not yet written or run a single line of LangChain code. That ends here.

Same Idea, Different Machinery: Pi and LangChain

Before we install anything, let us address the question you probably had after Chapter 1.

"Does Pi use LangChain?"

Natural question. You work with Pi. You have seen it read files, write code, run bash, and loop until you stop it. LangChain's agents do the same kind of thing. Are they the same under the hood?

Here is what the sources tell us:

Pi (your harness)

Pi is an open-source AI agent toolkit (MIT license). Its coding agent is a minimal terminal harness: a model, built-in tools (read, write, edit, bash), and an agentic loop that runs until the task is done.

Pi is open source — you can inspect every line of its agent loop and tool implementations at github.com/earendil-works/pi.

Pi does not use LangChain or LangGraph under the hood. It is an independent implementation of the same conceptual pattern.

LangChain Docs

LangChain describes the same conceptual pattern: a harness that connects a model to tools and repeats until done. Its create_agent is a high-level factory built on LangGraph.

LangChain is a general-purpose framework, agnostic about which model provider you use.

The bottom line: the idea is the same in both. The implementation is independent. Pi is an open-source harness you can inspect and learn from. LangChain is the framework you are learning here. This course uses Pi as a mental bridge — a concrete example you already have hands-on experience with — not as a dependency and not because one is built on the other.

Think of it this way: Pi and LangChain both ship the same triangle (model, tools, loop). They just pack it in different boxes. Pi is a ready-to-use terminal harness. LangChain is a Python framework you assemble yourself. Neither is the other's implementation. They are siblings in idea space, not parent and child in code space.

If that distinction feels fuzzy now, it will crystallize by the end of this lesson. The structure of the agent loop is the same everywhere. Master it once, and you can read any agent harness.

Installing LangChain

You need two things: a virtual environment (standard Python practice) and two pip install commands.

Open a terminal and run:

python3 -m venv .venv
source .venv/bin/activate   # Linux/macOS
# .venv\Scripts\activate    # Windows

Now install the core package plus one provider package. You need at least one provider package because LangChain itself does not contain any model. It connects to external models through provider packages:

pip install -U langchain
pip install -U langchain-openai

Provider package: a separate pip package that teaches LangChain how to talk to a specific model provider. langchain-openai covers GPT models. langchain-anthropic covers Claude models. langchain-ollama covers local models. You install the core once, then add whichever providers you need.

Why two installs?

LangChain is model-agnostic. The core package handles the agent framework, tools, and loop. Provider packages handle the model-specific API calls. This means you can switch from GPT to Claude by changing one line of code and one pip package, with zero changes to your agent logic.

If you have an OpenAI API key, set it as an environment variable:

export OPENAI_API_KEY="sk-..."
No key? No problem

You can read and understand every line of code in this lesson without running it. The concepts are the same whether the code executes or not. When you are ready to run, you need a key from platform.openai.com or a local Ollama install.

The API Shape: Four Moving Parts

Every LangChain agent you build will follow the same four-step pattern. Learn this skeleton once; every future chapter just fills in details:

# 1. Import
Bring in the factory function and the tool decorator
from langchain.agents import create_agent
from langchain.tools import tool
create_agent builds the harness. @tool turns a function into a callable tool.
# 2. Define a tool
A plain Python function with a docstring and type hints
@tool
def my_tool(param: str) -> str:
"""Description the model reads to decide when to call this."""
return f"Result: {param}"
@tool reads the function name, docstring, and type hints to build the schema the model sees.
# 3. Create the agent
Wire model + tools + system prompt together
agent = create_agent(
model="openai:gpt-4o",
tools=[my_tool],
system_prompt="You are a helpful assistant."
)
model = provider:model_id. tools = list of tool functions. system_prompt = instructions for the model.
# 4. Invoke
Send a message and get a response
result = agent.invoke({
"messages": [{"role": "user", "content": "..."}]
})
print(result["messages"][-1].content_blocks)
invoke runs the full loop. The result contains every message, including tool calls and responses.
Pause and predict

Read the skeleton above. Where do you think the loop lives? Is it visible in the code? Take ten seconds before reading on.

The loop is inside agent.invoke(). You do not see it because you do not have to write it. LangChain handles the repetition invisibly. You provide the model, the tools, and a message. The framework takes care of the rest.

Let us define each term precisely before we see them in action:

TermDefinition
Model identifierA string like "openai:gpt-4o" that tells LangChain which provider and which model to use. Format: provider:model_id.
ProviderThe company serving the model (OpenAI, Anthropic, Ollama). Each has its own package (langchain-openai, etc.).
System promptInstructions you give the model at the start of every conversation. Sets its behavior, tone, and constraints.
InvokeThe method that runs the agent. Sends your messages through the loop and returns the full conversation history.
MessageThe unit of conversation. A dictionary with role (user, assistant, system, tool) and content.
SchemaThe structure that describes a tool's inputs. LangChain infers it automatically from your function's type hints and docstring.

Your First Agent: Shipping Order Support

Enough definitions. Here is a complete, working LangChain agent with one tool that does not need a network connection or external data:

from langchain.agents import create_agent
from langchain.tools import tool

@tool
def lookup_shipping_status(order_id: str) -> str:
    """Look up the shipping status of an order by its order ID.
    Orders start with ORD- followed by four digits."""
    orders = {
        "ORD-1001": "Shipped. Estimated delivery in 3-5 business days.",
        "ORD-1002": "Processing. Estimated ship date: tomorrow.",
        "ORD-1003": "Delivered. Signed for on July 15, 2026.",
    }
    return orders.get(order_id,
        "Order not found. Please check the ID and try again.")

agent = create_agent(
    model="openai:gpt-4o",
    tools=[lookup_shipping_status],
    system_prompt=(
        "You are an order support agent. "
        "Use the lookup_shipping_status tool to check orders. "
        "Report the status clearly to the customer."
    ),
)

result = agent.invoke({
    "messages": [
        {"role": "user",
         "content": "Where is my order? The ID is ORD-1002."}
    ]
})

print(result["messages"][-1].content_blocks)
Read this code aloud

Read each line to yourself, out loud if possible. Point at each part:

"Import." (from langchain.agents import create_agent)

"Decorator." (@tool)

"Function name and docstring." (lookup_shipping_status, the description)

"Dict lookup." (orders.get(order_id, ...))

"Wire them together." (create_agent with model, tools, system_prompt)

"Send message." (agent.invoke with user asking about ORD-1002)

Notice what is missing: there is no for loop, no while, no manual routing of tool results. The agent just takes a message and returns a result. The loop is implicit.

Safe by design

This tool uses a dictionary lookup. It does not execute shell commands, access the filesystem, make network calls, or touch secrets. Every tool you write in this course starts safe. We add power gradually, with guardrails, starting in Chapter 4.

The Hidden Loop, Visible at Last

Here is exactly what happens when you call agent.invoke(). This sequence is the same whether you are using LangChain, Pi, or any other agent harness:

1
User message enters. Your {"role": "user", "content": "Where is my order? ORD-1002"} is wrapped in messages and sent to the model.
2
Model decides. The model reads the system prompt, sees the tool definitions (name, description, parameters), and decides: "I should call lookup_shipping_status with order_id="ORD-1002"." It outputs a structured tool call request.
3
Loop intercepts. The harness inside invoke() sees the tool call output. It does not forward it to you yet. Instead, it extracts the tool name and the parsed arguments.
4
Tool executes. The harness calls your Python function directly: lookup_shipping_status(order_id="ORD-1002"). Your function runs and returns the string "Processing. Expected ship date: tomorrow."
5
Result feeds back. The harness wraps the return value as a ToolMessage and appends it to the conversation: role=assistant (tool_call) -> role=tool (result).
6
Model decides again. The model now has the full history: user question, its own tool call, and the tool result. It decides whether to call another tool or produce a final answer.
7
Answer returned. The model outputs a final text response. The harness sees it is not a tool call and stops the loop. The full message list is returned as result["messages"].

This is the same loop Pi's coding agent runs when you ask it to read a file or edit code. Pi's model emits a tool call for read. The harness runs it. The file content feeds back as a result. Pi decides the next step. The only difference: Pi's coding-agent tools are read, write, edit, bash. Your LangChain tools are whatever Python functions you define with @tool.

Model does not call functions

This is the single most important thing to understand: the model never calls your Python function directly. It outputs a structured request (a tool call with name + arguments). The harness reads that request, calls your function, and feeds back the result. The model is a planner, not an executor. It suggests. The harness executes.

Make the Loop Visible

So far you have taken the loop on faith. invoke() hides every intermediate step. It runs the full loop internally and hands you only the final answer object. That is fine for production, but terrible for learning. Let us crack it open.

LangChain agents can stream their execution node by node. Instead of waiting for the full result, you see each stage as it happens: the model emitting a tool call, the Python tool running, the model responding again, the loop ending. Streaming transforms a black box into a transparent pipeline.

Why stream matters

Every future debugging skill depends on being able to watch what your agent actually does, not just what you expect it to do. Streaming is your window into the loop.

The Path a Message Travels

Here is the exact path every message follows through the agent. Each box is a node you can observe in the stream output:

User
Message → Model
(tool call?) → Python
Tool → Tool
Result → Decide → Final
Answer → END

The flow from user message through model, tools, and decision back to model (loop) or final answer (end). The decision node checks the model's latest tool_calls field to determine the next step.

Watching with stream()

Instead of invoke(), call stream() with stream_mode="updates". Each yielded value is a dictionary whose keys are node names ("model", "tools", "__end__"). You see state changes, not raw tokens:

for update in agent.stream(
    {"messages": [{"role": "user", "content": "Where is ORD-1002?"}]},
    stream_mode="updates",
    version="v2",
):
    for node_name, output in update.items():
        if node_name == "model":
            msg = output["messages"][-1]
            if msg.tool_calls:
                tc = msg.tool_calls[0]
                print(f"[MODEL] calling: {tc['name']}({tc['args']})")
            else:
                print(f"[MODEL] final: {msg.content[:120]}")
        elif node_name == "tools":
            tm = output["messages"][-1]
            print(f"[TOOL]  {tm.name} → {tm.content[:120]}")
        elif node_name == "__end__":
            print("[END]  Agent finished")

This loop iterates over updates from each graph node. You never see the model's raw token stream (that is a differentstream_mode called "messages"). You see state changes — the high-level trace of what each node produced.

What the Output Looks Like

Here is the trace you would see when the agent with lookup_shipping_status processes "Where is ORD-1002?":

[MODEL] calling: lookup_shipping_status({'order_id': 'ORD-1002'})
[TOOL]  lookup_shipping_status → Processing. Estimated ship date: tomorrow.
[MODEL] final: Your order ORD-1002 is currently being processed...
[END]   Agent finished

Reading top to bottom:

  1. Line 1 — The model node ran and emitted a tool call for lookup_shipping_status with order_id="ORD-1002". Non-empty tool_calls means the loop continues.
  2. Line 2 — The tools node executed your Python function. The harness called it directly and wrapped the return value.
  3. Line 3 — The model node ran again with the tool result in history. It produced a text answer with empty tool_calls — loop ends.
  4. Line 4 — The graph reached its end node.
Why not just use invoke()?

invoke() swallows all of this. It runs the full loop internally and returns the final result["messages"] object. You never see the intermediate tool calls, tool results, or the moment the model switches from reasoning to answering. stream() shows you everything — including where your agent spends its time and whether it is calling tools efficiently.

Exercise: Read This Code Aloud

Pause. Read aloud. Then answer.

Below is a second agent. It has two tools. Read the code aloud, then answer the questions:

from langchain.agents import create_agent
from langchain.tools import tool

@tool
def get_discount_code(department: str) -> str:
    """Get a current discount code for a product department.
    Departments: electronics, home, clothing."""
    codes = {
        "electronics": "TECH20",
        "home": "HOME15",
        "clothing": "STYLE10",
    }
    return codes.get(department, "No current discount for that department.")

@tool
def check_return_policy(item_type: str) -> str:
    """Check the return policy for a type of item.
    Item types: electronics, furniture, clothing."""
    policies = {
        "electronics": "30-day return. Must include all accessories.",
        "furniture": "14-day return. Must be in original packaging.",
        "clothing": "60-day return. Tags must be attached.",
    }
    return policies.get(item_type, "Check receipt for policy details.")

agent = create_agent(
    model="openai:gpt-4o",
    tools=[get_discount_code, check_return_policy],
    system_prompt="You are a retail customer service agent.",
)

1. How many tools does this agent have? What are their names?

2. What tells the model when to call get_discount_code vs check_return_policy?

3. If the user asks "Can I return my laptop?" and "Is there a sale on electronics?" in one message, how many tool calls will the agent make?

Reveal answers

1. Two tools: get_discount_code and check_return_policy.

2. The docstrings are what the model reads. get_discount_code's docstring says "Get a current discount code," which matches the question about sales. check_return_policy's docstring mentions "return policy." The model reads these descriptions to decide which tool fits. This is why writing clear docstrings is critical.

3. The agent will likely make two tool calls (one for the return policy, one for the discount code), then synthesize both results into a single answer. If the model supports parallel tool calling (GPT-4o does), it may even call both at the same time. The loop runs once but processes multiple tool calls in a single turn.

What This Agent Does Not Do Yet

Your first agent is a beautiful thing. But it is also limited. Before you get excited and try to build a production system, here is what our current agent does not do. These gaps are intentional — each one is a future chapter:

No memory

Each invoke starts fresh. The agent does not remember the previous conversation. Short-term memory (checkpointers) comes in Chapter 9.

No custom branching

Take it or leave it: the agent calls tools or answers. You cannot add conditional logic between steps. That is LangGraph territory (Chapters 6-8).

No durable workflow

If the process crashes mid-loop, the conversation is lost. Durable execution with automatic resume comes with LangGraph persistence.

No middleware

No guardrails, no retries, no logging middleware between the model and tools. That comes in Chapter 5.

What you have built

None of those limitations matter right now. You have built the core: a model that reasons, tools that act, and a loop that connects them. Everything else is infrastructure around this triangle. The rest of this course is about adding that infrastructure, one layer at a time, without touching the core pattern you just learned.
