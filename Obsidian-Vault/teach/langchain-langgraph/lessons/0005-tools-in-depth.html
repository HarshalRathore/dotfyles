Tools in Depth: Give the Model a Safe Way to Act

In Chapter 4 you controlled the model and its messages. Now you will give that model carefully described Python functions, then watch the harness carry a request from AIMessage to ToolMessage and back.

A model can decide that it needs information or an action. It cannot, by itself, query your order table, read your database, or call your business logic. A tool is the contract that lets it ask your Python code to do one bounded thing.

The model chooses when a tool is useful and supplies arguments. Your code owns what the tool actually does. That separation is the important idea.

This chapter's win

By the end of this chapter you will have a safe, deterministic order assistant. It will use two typed tools, pass user context through ToolRuntime, handle a failed lookup as a message the model can understand, and keep the provider choice in one model string.

A Tool Is a Contract

Start with an ordinary Python function. The @tool decorator turns it into a LangChain tool that an agent can expose to a model.

from langchain.tools import tool

ORDERS = {
    "ORD-1042": "packed and leaving the warehouse",
    "ORD-1088": "delivered yesterday",
}

@tool
def lookup_order(order_id: str) -> str:
    """Look up the shipping status for one order ID."""
    if order_id not in ORDERS:
        raise ValueError(f"Unknown order: {order_id}")
    return ORDERS[order_id]

print(lookup_order.name)
# lookup_order
print(lookup_order.description)
# Look up the shipping status for one order ID.
print(lookup_order.args_schema.model_json_schema())

Three pieces make the contract useful:

Python sourceWhat the model receives
Function nameThe default tool name: lookup_order.
Type hint: order_id: strAn input schema saying the tool needs one string argument.
DocstringThe description that helps the model decide when this tool fits.
The boring rule that prevents bad calls

Type hints are not decoration here. They define the tool's input schema. The docstring is not a comment for humans only; by default it becomes the tool description the model uses. Keep both precise, short, and honest.

Predict the Schema

Before reading the answer, what should appear in lookup_order.args_schema.model_json_schema()["properties"]? The function has one annotated parameter and no optional inputs.

Reveal the answer

You should see one property named order_id with a string type. The model never sees the Python ORDERS dictionary or the function's internal if statement. It sees a name, a description, and the arguments it is allowed to construct.

Do not hide the contract

A tool with a vague name, missing type hints, or a misleading docstring gives the model a bad interface. Fix the tool description before adding a clever prompt.

Read the Tool Call

Chapter 4 corrected an easy confusion: the model does not execute your Python function. It emits an AIMessage containing a tool-call request. Your application or the agent harness executes the tool, wraps the result in a ToolMessage, and sends the messages back to the model.

HumanMessage → AIMessage + tool_calls → ToolMessage → AIMessage

At the model layer, the loop is visible:

from langchain.messages import HumanMessage

model_with_tools = model.bind_tools([lookup_order])
messages = [HumanMessage("Where is order ORD-1042?")]

ai_msg = model_with_tools.invoke(messages)
messages.append(ai_msg)

for tool_call in ai_msg.tool_calls:
    tool_message = lookup_order.invoke(tool_call)
    messages.append(tool_message)

final_response = model_with_tools.invoke(messages)
print(final_response.content)

The important identity is tool_call_id. The model puts an ID on its request. The resulting ToolMessage carries the same ID so the model can match a result to the request that caused it.

AIMessage
tool_calls = [{"name": "lookup_order",
"args": {"order_id": "ORD-1042"},
"id": "call_1"}]
The model proposes a function name, arguments, and correlation ID. It has not run Python yet.
ToolMessage
content = "packed and leaving the warehouse"
tool_call_id = "call_1"
Your tool ran. Its result is now a message that points back to the exact model request.
AIMessage
content = "Order ORD-1042 is packed..."
The model sees the tool result and decides whether it can answer or needs another tool.
Model capability caveat

bind_tools makes tools available to a chat model. The model still needs tool-calling support, and support differs by provider and model. The interface is uniform; the capability is not.

Compose Tools in an Agent

You usually do not write that loop yourself. create_agent is the harness that binds the tools, asks the model what to call, executes the selected functions, appends results, and continues until the model produces a final answer.

from langchain.agents import create_agent

@tool
def get_shipping_eta(order_id: str) -> str:
    """Return the estimated delivery window for one order ID."""
    if order_id not in ORDERS:
        raise ValueError(f"Unknown order: {order_id}")
    return "tomorrow afternoon"

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[lookup_order, get_shipping_eta],
    system_prompt=(
        "You are an order assistant. "
        "Use tools for order facts. Never invent a status."
    ),
)

result = agent.invoke({
    "messages": [{
        "role": "user",
        "content": "Where is ORD-1042 and when should it arrive?",
    }]
})

The list is the composition boundary: tools=[lookup_order, get_shipping_eta]. The model sees both contracts and chooses one or both based on the request. It does not see your Python implementation.

Trace it like Chapter 3

Inspect result["messages"]. You should find the user message, one or more AIMessage objects with tool calls, matching ToolMessage results, and a final AIMessage. The harness is still the same model plus loop you already know. Tools are the new participants.

No guarantee of one call

The model may call one tool, both tools, the same tool again, or no tool at all. Your system prompt can set expectations, but the model's decision is not a hard control flow guarantee. Validate important actions in Python.

Official source

The Agents tools section shows how a callable or LangChain tool is passed to create_agent. The create_agent reference documents the factory contract.

ToolRuntime: Context Without Schema Noise

A tool sometimes needs information that the model should not invent or supply: the authenticated user, a session identifier, or current conversation state. ToolRuntime injects that runtime information into the Python function.

from dataclasses import dataclass
from langchain.tools import ToolRuntime, tool

@dataclass
class UserContext:
    user_id: str

USER_TIERS = {
    "user_123": "premium",
    "user_456": "standard",
}

@tool
def get_account_tier(runtime: ToolRuntime[UserContext]) -> str:
    """Return the current user's account tier."""
    return USER_TIERS.get(runtime.context.user_id, "unknown")

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[get_account_tier],
    context_schema=UserContext,
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "What account tier am I on?"}]},
    context=UserContext(user_id="user_123"),
)

The model sees a zero-argument tool named get_account_tier. It does not see runtime as an input it must construct. LangChain recognizes the ToolRuntime annotation, injects the value, and hides that parameter from the model-visible schema.

runtime and config are reserved parameter names. Do not use them as ordinary user-supplied tool arguments. LangChain uses them for injected execution data.

Errors Need a Path Back

Tools are ordinary Python functions, so they can fail: an order ID may not exist, a database may be unavailable, or an argument may be invalid. If the harness turns every exception into a dead run, the model has no chance to recover.

LangChain's agent middleware can catch a tool exception and return an error ToolMessage tied to the original call:

from typing import Callable
from langchain.agents.middleware import wrap_tool_call
from langchain.messages import ToolMessage
from langchain.tools.tool_node import ToolCallRequest

@wrap_tool_call
def handle_tool_errors(
    request: ToolCallRequest,
    handler: Callable[[ToolCallRequest], ToolMessage],
) -> ToolMessage:
    try:
        return handler(request)
    except Exception:
        return ToolMessage(
            content="That tool could not complete the request. Check the input and try again.",
            tool_call_id=request.tool_call["id"],
        )

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[lookup_order, get_shipping_eta],
    middleware=[handle_tool_errors],
)

The error does not magically become a successful answer. It becomes model-readable context. The model may explain the problem, ask for a corrected ID, or choose another tool. That decision is still model behavior, so important business actions need validation outside the model.

Retry is a separate policy

LangChain also documents ToolRetryMiddleware for retrying transient failures. Do not confuse retrying a failed function with returning a useful error message. One is a recovery policy; the other is a communication path.

The Safe Order Assistant Lab

Put the pieces together. This lab has no network tools and no destructive actions. It uses a tiny in-memory order table so you can reason about the messages before you connect real services.

import os
from dataclasses import dataclass
from typing import Callable

from langchain.agents import create_agent
from langchain.agents.middleware import wrap_tool_call
from langchain.messages import ToolMessage
from langchain.tools import ToolRuntime, tool
from langchain.tools.tool_node import ToolCallRequest

ORDERS = {
    "ORD-1042": "packed and leaving the warehouse",
    "ORD-1088": "delivered yesterday",
}
USER_TIERS = {"user_123": "premium", "user_456": "standard"}

@dataclass
class UserContext:
    user_id: str

@tool
def lookup_order(order_id: str) -> str:
    """Look up the shipping status for one order ID."""
    if order_id not in ORDERS:
        raise ValueError(f"Unknown order: {order_id}")
    return ORDERS[order_id]

@tool
def get_account_tier(runtime: ToolRuntime[UserContext]) -> str:
    """Return the current user's account tier."""
    return USER_TIERS.get(runtime.context.user_id, "unknown")

@wrap_tool_call
def handle_tool_errors(request: ToolCallRequest, handler) -> ToolMessage:
    try:
        return handler(request)
    except Exception:
        return ToolMessage(
            content="The lookup failed. Ask the user to check the order ID.",
            tool_call_id=request.tool_call["id"],
        )

agent = create_agent(
    model=os.getenv("MODEL", "openai:gpt-5.5"),
    tools=[lookup_order, get_account_tier],
    context_schema=UserContext,
    middleware=[handle_tool_errors],
    system_prompt="Use tools for order facts. Never invent a status.",
)

result = agent.invoke(
    {"messages": [{
        "role": "user",
        "content": "Check ORD-1042 and tell me my account tier.",
    }]},
    context=UserContext(user_id="user_123"),
)

for message in result["messages"]:
    print(type(message).__name__, message)
Run the thought experiment

Predict the message order before running anything: the user message, an AIMessage with calls for the order and account tier, two ToolMessage results, then a final AIMessage. The exact order and number of calls are model decisions, but every tool result must point to its matching call ID.

Now change the request to Check ORD-9999 and tell me my account tier. The lookup raises an exception. The middleware turns it into a ToolMessage. The agent can now explain the missing order instead of losing the entire run.

The durable boundary

The model chooses and explains. The tool validates and acts. ToolRuntime supplies trusted execution context that the model should not invent. Middleware decides how failures travel back through the loop.

Predict the Message

What does this tool invocation return?

Read the code and predict the type name and the correlation ID. The tool call is already in the shape emitted by an AIMessage.

tool_call = {
    "name": "lookup_order",
    "args": {"order_id": "ORD-1042"},
    "id": "call_1",
    "type": "tool_call",
}

result = lookup_order.invoke(tool_call)
print(type(result).__name__)
print(result.tool_call_id)
Reveal the answer

The type name is ToolMessage. The printed ID is call_1. Passing the full tool-call dictionary lets the decorated tool execute the arguments and return a message already linked to the model's request.
