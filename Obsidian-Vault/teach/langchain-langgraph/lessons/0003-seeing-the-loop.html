Seeing the Loop: Messages, Tool Calls, and Finish Conditions

In Chapter 2 you called agent.invoke() and got an answer back. The loop was hidden inside. In this chapter we crack it open and watch every step.

We know the loop exists. Chapter 2 proved it: you wrote a @tool function, wired it to create_agent, called invoke(), and the agent returned an answer. The model reasoned, called your tool, used the result, and produced a final response — all inside that one function call.

But what exactly happened at each step? How did the framework know to stop? How did it know to keep going? What did the messages look like at every stage?

In Chapter 2's "Make the Loop Visible" section, you saw a numbered sequence: message in, model decides, harness intercepts, tool executes, result feeds back, model decides again, answer returned. That sequence is the conceptual loop. In this chapter you will see the actual loop — the exact messages, the streaming trace, and the finish condition that tells the framework when to stop.

This chapter is a trace

You will not build anything new here. You will watch. The skill this chapter teaches is reading the trace. Every agent debugging session starts with looking at the messages. Master this and you will never wonder "what is my agent doing?"

The Normal Finish Condition

Here is the single most important rule in the entire agent loop. Memorize it:

The loop's finish condition

The agent loop ends when the latest AIMessage produced by the model contains an empty (or absent) tool_calls list. When tool_calls is empty, the graph routes to __end__. When tool_calls has entries, the loop continues.

This is the only stop/go rule the loop evaluates. The model's latest output determines whether the loop continues or terminates.

Let us trace through the two cases:

1
Model receives input. The harness sends the full message history including the user's question and the tool schemas.
2
Model emits a response. The model outputs an AIMessage which may contain content (text) and/or a tool_calls list.
3
Harness inspects tool_calls. If tool_calls is a non-empty list, the harness extracts each call (tool name + arguments) and executes the matching Python function.
4
Tool results become ToolMessages. Each function's return value is wrapped in a ToolMessage that carries the tool_call_id linking it back to the call that produced it. These messages are appended to the history.
5
Model sees updated history. The conversation now includes: user question, model's tool call, tool result. The model generates a new response. If it calls another tool, go to step 3. If it produces a plain text answer with no tool_calls, go to step 6.
6
Loop ends. The graph routes to __end__. The full message list is returned to the caller.
What "empty tool_calls" looks like

An AIMessage produced by most providers has a tool_calls field that defaults to an empty list [] when the model decides not to call any tool. The harness checks if not aimessage.tool_calls — if the list is empty (falsy), the loop terminates. If the list has items, the loop continues.

Messages You Need to Know

The agent loop runs on messages. Every piece of data that flows through the loop is wrapped in a typed message object. Here are the four you will see in every trace:

Message TypeCreated WhenKey FieldsPurpose
HumanMessage User sends input content Carries the user's question or instruction. The starting point of every conversation.
AIMessage Model responds content, tool_calls The model's output. content holds text. tool_calls holds a list of structured tool requests (empty when answering directly).
ToolMessage Tool finishes content, tool_call_id Carries the result of a tool execution. tool_call_id links it to the specific AIMessage tool_call that triggered it.
SystemMessage Session starts content System prompt set at agent creation. Injected at the start of the conversation to set model behavior.

The tool_calls field on AIMessage deserves special attention. It is a list of dictionaries, each containing:

FieldTypeDescription
namestringThe name of the tool to call (matches your @tool function name).
argsdictThe arguments the model wants to pass, as key-value pairs.
idstringA unique identifier for this specific tool call. Used by ToolMessage.tool_call_id to link result to request.
The link is the ID

Each tool_call gets a unique id (a UUID string). When the tool result comes back, the harness produces a ToolMessage with tool_call_id set to that same ID. This is how the model knows which result belongs to which call — critical when the model makes multiple parallel tool calls.

Stream, Stream Mode, Update

When you call agent.invoke(), the entire loop runs to completion before anything is returned. You get the final message list, but you never see the intermediate steps as they happen.

To watch the loop in motion, you use streaming:

ConceptDefinition
Stream A method that yields per-node updates as the graph executes, instead of waiting for the final result. Each yield represents one node completing its work.
stream_mode='updates' Tells the graph to emit only the state changes made by each node. You see what each node produced, not the full accumulated state.
version='v2' The current streaming API version. V2 normalises the output format across different graph types and ensures consistent key naming.
Node name The label of the graph node that just executed. In create_agent graphs, you typically see "model" (the LLM call) and "tools" (tool execution).
Official stream docs

Read the full streaming guide at docs.langchain.com/oss/python/langgraph/streaming and the API reference at reference.langchain.com/python/langgraph/graph/stream.

Watching a Real Trace

Let us reuse the lookup_shipping_status tool from Chapter 2 and stream its execution step by step. This is the same agent you built before, but now we will watch every node fire:

from langchain.agents import create_agent
from langchain.tools import tool

@tool
def lookup_shipping_status(order_id: str) -> str:
    """Look up the shipping status of an order by its order ID.
    Orders start with ORD- followed by four digits."""
    orders = {
        "ORD-1001": "Shipped. Estimated delivery in 3-5 business days.",
        "ORD-1002": "Processing. Estimated ship date: tomorrow.",
        "ORD-1003": "Delivered. Signed for on July 15, 2026.",
    }
    return orders.get(order_id,
        "Order not found. Please check the ID and try again.")

agent = create_agent(
    model="openai:gpt-4o",   # any provider works
    tools=[lookup_shipping_status],
    system_prompt=(
        "You are an order support agent. "
        "Use the lookup_shipping_status tool to check orders. "
        "Report the status clearly to the customer."
    ),
)

# Stream the execution node by node
for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "Where is my order? ORD-1002"}]},
    stream_mode="updates",
    version="v2",
):
    for node_name, data in chunk.items():
        if node_name == "model":
            msg = data["messages"][-1]
            if msg.tool_calls:
                tool_name = msg.tool_calls[0]["name"]
                tool_args = msg.tool_calls[0]["args"]
                print(f"[MODEL] calling tool: {tool_name}({tool_args})")
            else:
                print(f"[MODEL] final: {msg.content}")
        elif node_name == "tools":
            tool_result = data["messages"][-1].content
            print(f"[TOOL] result: {tool_result}")

print("[END]")
Provider-neutral note

The code above uses "openai:gpt-4o" as an example model identifier. Any model provider works — "anthropic:claude-opus-4", "ollama:llama3", or any other provider with a LangChain integration package. The loop pattern, finish condition, and stream output are the same regardless.

When you run this code, the output will look something like this (actual model output varies):

[MODEL] calling tool: lookup_shipping_status({'order_id': 'ORD-1002'})
[TOOL] result: Processing. Estimated ship date: tomorrow.
[MODEL] final: Your order ORD-1002 is being processed and is expected to ship tomorrow. You should receive tracking information once it ships.
[END]

The stream yielded three events: one from the model node (where the LLM decided to call a tool), one from the tools node (where the Python function ran), and one more from the model node (where the LLM produced the final answer after seeing the tool result).

Reading the Output

Let us annotate that trace line by line so you know exactly what each part means:

MODEL calling tool: lookup_shipping_status({'order_id': 'ORD-1002'})
The graph's model node executed. The LLM received the user message plus tool schemas and decided to call lookup_shipping_status with order_id="ORD-1002". The AIMessage has a non-empty tool_calls list, so the loop continues.
TOOL result: Processing. Estimated ship date: tomorrow.
The graph's tools node executed. The harness took the tool call from the AIMessage, called lookup_shipping_status(order_id="ORD-1002") directly, and wrapped the return value as a ToolMessage. This message is appended to the conversation history.
MODEL final: Your order ORD-1002 is being processed...
The graph's model node executed again. This time the LLM had the full history: user question, its own tool call, and the tool result. It decided no more tools were needed and produced a plain text answer. The AIMessage's tool_calls is empty [], so the loop ends.
END
The graph routed to __end__. No more nodes to execute. The full message list is available as the return value.

Every agent trace follows this pattern. A run that makes multiple tool calls produces a longer sequence, but the structure is the same: MODEL → TOOL → MODEL → TOOL → MODEL → END.

The Automaton: Three States, Two Transitions

Every create_agent agent is a finite-state machine. Three nodes, two conditional transitions, one growing messages[] state. Once you internalize this diagram, you can read any LangGraph trace.

The three states (nodes)

model — The LLM inference node. Receives the full message history, picks tool schemas from the agent definition, generates the next AIMessage. This is where the HTTP request to the provider happens.

tools — Executes each tool call from the model's output. LangChain runs the registered Python function with the arguments the model chose, wraps the return value in a ToolMessage, and appends it to state.

__end__ — Terminal state. Once reached, no more nodes execute. The full messages[] list becomes the return value.

How the edges decide

The only conditional fork in the entire automaton is between model and __end__. LangGraph inspects the model's latest AIMessage.tool_calls field. The decision is binary:

  • tool_calls present (!= [] / finish_reason = "tool_calls") → follow the gold edge to tools
  • no tool_calls (== [] / finish_reason = "stop") → follow the red edge to __end__

The tools node always routes back to model via the green edge after executing — a tool cannot end the session; only the model can.

The Model Suggests, the Framework Executes

This distinction is so important it deserves its own section. Read it twice:

The model never runs your code

The model emits structured JSON that describes a tool call. LangChain parses that JSON, matches the tool name to a registered Python function, calls that function with the parsed arguments, wraps the return value as a ToolMessage, and appends it to the history.

The model is a planner. It suggests what to do. The framework is the executor. It does the actual work and reports back.

Here is exactly what the model emits vs what the framework runs:

# What the model emits (JSON)
The model outputs structured text — it never calls a function.
{
"name": "lookup_shipping_status",
"args": {"order_id": "ORD-1002"},
"id": "call_abc123"
}
This is a tool call. The model produces it as part of its text output, formatted as structured JSON. No Python was executed.
# What the framework runs
The harness reads the JSON and calls your function.
lookup_shipping_status(order_id="ORD-1002")
This is the actual Python call. The harness extracted the tool name + args and invoked your @tool function directly. The result becomes a ToolMessage.
You cannot skip the harness

The model cannot call your function directly. It has no access to your Python runtime, your memory, or your filesystem. It only produces text. The harness translates that text into actions. This is what makes the agent pattern safe: the model can only suggest what should happen; you control what actually runs.

Thinking Tokens and Reasoning

Some modern LLMs (OpenAI's o-series models, Anthropic's Claude Opus) include reasoning or thinking tokens — internal monologue that the model produces before arriving at its final answer. These are not part of the standard agent trace and require careful handling:

ConceptDetail
Thinking / reasoning Internal chain-of-thought the model generates before producing its visible output. Some providers expose it as a separate content block; others do not expose it at all.
Provider-dependent OpenAI o-series models can expose reasoning_summary or token counts rather than the full reasoning text. Anthropic Claude Opus may include thinking blocks when enabled. Smaller models often have no reasoning output at all.
Explicit settings required Thinking/reasoning features may require specific model configuration parameters. They are not guaranteed to appear and are not equivalent to the trace events shown in this chapter.
NOT trace events The [MODEL] and [TOOL] events in your stream trace are graph node executions. Reasoning tokens are model internals. Do not confuse them. Do not build logic that depends on private reasoning output.
Do not promise or print private reasoning

Never build an agent that depends on reading the model's reasoning or thinking tokens. These are not part of the stable API. They may change, disappear, or require explicit user consent depending on the provider. The visible trace events (message types, tool_calls, stream output) are the contract you should rely on.

Updates vs Values

When you stream an agent's execution, you have two choices for what the stream yields:

ModeWhat it yieldsWhen to use
stream_mode='updates' Only the state changes produced by each node. Each chunk shows what that node added or modified. Compact and readable. Use this. It is the default choice for debugging, logging, and displaying agent progress to users.
stream_mode='values' The full accumulated state after each node. Every chunk includes the entire message list plus any private graph channels. Avoid unless you specifically need the full state dump. It is verbose and may include internal graph channels that are not intended for casual reading.
Warning: 'values' dumps everything

stream_mode='values' does not just include messages. It also includes any private state channels the graph uses internally. Logging these casually could expose internal routing data or produce enormous output. Stick to stream_mode='updates' for routine tracing.

To see the difference: with updates, a model node that calls a tool yields just the new AIMessage. With values, that same node yields the entire message history (user message + system prompt + all prior turns) plus any graph-internal state. For a multi-turn agent, values grows linearly with each step.

Other Ways the Loop Can End

The normal finish condition (empty tool_calls on AIMessage) covers 95% of agent runs. But the loop can end in a few other ways:

Middleware can jump to end

A guardrail or routing middleware can send the graph directly to __end__ before the model even decides. For example, content filtering middleware might terminate a run that asks the agent to do something outside its scope.

Structured output can finish

Some agents use structured output (a Pydantic model as the response format). When the graph is configured to produce a specific output schema, the loop may end once the structured output node completes, even if the latest AIMessage has tool_calls.

Errors and recursion limits

If a tool raises an unhandled exception, the graph stops with an error. LangGraph also has a configurable recursion_limit (default 25) that forces termination to prevent infinite loops. Both produce error traces rather than normal completion.

Graph runs out of nodes

If the graph topology has no more edges to follow (a node with no outgoing edge to another node), execution stops. In a standard create_agent graph this does not happen, but custom LangGraph graphs (Chapters 6-8) can have terminal nodes other than __end__.

For now, focus on the normal case: empty tool_calls means stop, non-empty means continue. The other exits are edge cases you will encounter as you build more complex agents.

Trace Reading Practice

Below are three lines from an agent trace. Read them carefully, then predict what the fourth line will be. The agent uses lookup_shipping_status and get_return_policy as tools.

[MODEL] calling tool: lookup_shipping_status({'order_id': 'ORD-1001'})
[TOOL] result: Shipped. Estimated delivery in 3-5 business days.
[MODEL] calling tool: get_return_policy({'item_type': 'electronics'})
What is line 4?

Correct answer: [TOOL] result: 30-day return. Must include all accessories.

Why: The model saw the shipping status result (ORD-1001 is shipped) and decided it also needed the return policy to answer the user's question fully. It called get_return_policy with item_type="electronics". The next node to execute is the tools node, which will run the function and produce a ToolMessage. After that, the model receives both results and decides whether to call another tool or produce a final answer.

The trace pattern is predictable: MODEL (tool call) always leads to TOOL (result). Only when the model produces a plain text answer does END follow.
