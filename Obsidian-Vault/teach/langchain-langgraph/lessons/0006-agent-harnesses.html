Agent Harnesses: Put Policy Around the Loop

In Chapter 5 you gave the model tools. Now you will control the loop around those tools: prompts, limits, retries, and guardrails.

Pi gave you a useful mental model: model + tools + loop. LangChain calls the thing around that loop a harness. The harness decides what context reaches the model, which tools are available, what policies run before and after a step, and when the run must stop.

create_agent is LangChain's configurable harness. It gives you a working model-tools loop first. Middleware lets you add policy at the seams without rebuilding the loop.

This chapter's win

You will turn the Chapter 5 order assistant into a bounded harness: a deterministic input gate, a model-call budget, and a retry policy that distinguishes transient tool failures from permanent bad input.

Agent = Model + Harness

An agent still calls a model, lets it choose tools, executes those tools, and repeats until the model stops requesting tools. The harness is the policy layer around those steps.

Input → Guardrails → Model → Tools → Policy

The default loop is useful. The engineered loop is bounded and observable.

The boundary

A system prompt is model guidance. Middleware is application control. If a rule must hold even when the model ignores instructions, enforce it in Python middleware or tool code.

System prompts are not access control

"Never send money" is an instruction. A middleware policy that interrupts a transfer tool is a control. Keep important validation in deterministic Python.

Static Versus Dynamic Instructions

system_prompt= is the simple static case. When the prompt must change with trusted runtime context, use middleware. The prompt can mention a user's plan or locale; the permission check still belongs in code.

agent = create_agent(
    model="openai:gpt-5.5",
    tools=tools,
    system_prompt=(
        "You are a concise order assistant. "
        "Use tools for facts; never invent an order status."
    ),
)
Official source

system_prompt accepts a string or SystemMessage. For dynamic prompts, the official docs point to middleware and the @dynamic_prompt shortcut. See the Agents docs and Custom middleware docs.

Middleware: Hooks Around Each Step

Middleware is not a second runtime. It runs inside the compiled LangGraph that create_agent returns. There are two hook styles.

Node-style
before_agent
before_model
after_model
after_agent
Run at named points. Return state updates or short-circuit a run. before_agent and after_agent run once per invocation; model hooks run per model iteration.
Wrap-style
wrap_model_call
wrap_tool_call
Surround one model or tool call. Decide whether the handler runs zero, one, or multiple times. Useful for retries, transformation, and interception.

That distinction is the design shortcut:

  • Need a check once at the beginning? Use before_agent.
  • Need to observe every model response? Use after_model.
  • Need to retry a specific call? Use a wrap hook or built-in retry middleware.
  • Need to intercept a tool result? Use wrap_tool_call or tool middleware.

Predict the Hook Count

An agent makes three model calls because it uses two tools before answering. How many times does each hook run?

Reveal the answer

before_agent runs once and after_agent runs once. before_model and after_model run three times each, once around every model call. They are not one-time setup hooks.

Official source

The Custom middleware docs define node-style and wrap-style hooks and show how each hook updates or intercepts agent execution.

Build a Deterministic Guardrail

A guardrail is a check that prevents or changes unsafe behavior. The simplest useful guardrail runs before the model sees the request.

from typing import Any

from langchain.agents.middleware import AgentState, before_agent
from langgraph.runtime import Runtime

BLOCKED_WORDS = {"delete", "transfer"}

@before_agent(can_jump_to=["end"])
def safety_gate(
    state: AgentState,
    runtime: Runtime,
) -> dict[str, Any] | None:
    if not state["messages"]:
        return None

    first_message = state["messages"][0]
    if first_message.type != "human":
        return None

    if any(word in first_message.content.lower() for word in BLOCKED_WORDS):
        return {
            "messages": [{
                "role": "assistant",
                "content": "This assistant cannot perform that operation.",
            }],
            "jump_to": "end",
        }
    return None

The gate is deterministic: it does not ask another model whether the request is safe. It returns a state update and jumps to the end before the normal loop begins.

Policy is not magic

This example is a teaching guardrail, not a complete security system. Keyword checks miss paraphrases. Authorization, validation, and dangerous side-effect controls must still live at the tool or service boundary.

Official source

The Guardrails docs show deterministic before_agent checks and explain the difference between deterministic and model-based guardrails.

Bound the Loop

A model can make a reasonable decision and still spend too many calls. A harness needs a budget.

from langchain.agents.middleware import ModelCallLimitMiddleware

agent = create_agent(
    model="openai:gpt-5.5",
    tools=tools,
    middleware=[
        safety_gate,
        ModelCallLimitMiddleware(
            run_limit=3,
            exit_behavior="end",
        ),
    ],
)
LimitProtectsScope
run_limitOne invocation from making too many model calls.Resets on the next invocation.
thread_limitA persistent conversation from accumulating too many calls.Requires a checkpointer.
ToolCallLimitMiddlewareExpensive or risky tool execution.Global or one named tool.

exit_behavior="end" stops gracefully when the limit is reached. exit_behavior="error" raises instead. Pick based on whether the caller needs a normal terminal state or an explicit failure.

Cost control is behavior control

Limits are not only billing protection. They make the agent's possible behavior finite, which makes testing and incident analysis easier.

Official source

The ModelCallLimitMiddleware docs cover per-run and per-thread limits. The same page documents ToolCallLimitMiddleware for global or tool-specific budgets.

Retry the Right Failure

Retries are a policy, not a guarantee that a request is valid. A timeout may be transient. An unknown order ID is usually permanent bad input.

from langchain.agents.middleware import ToolRetryMiddleware

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[lookup_order],
    middleware=[
        ToolRetryMiddleware(
            tools=["lookup_order"],
            max_retries=2,
            retry_on=(TimeoutError,),
            on_failure="continue",
        ),
    ],
)
PolicyResult after retries are exhausted
on_failure="continue"Return a ToolMessage error so the model can respond.
on_failure="error"Re-raise the exception and stop the agent execution.
retry_on=(TimeoutError,)Retry only the failure type you consider transient.

This is why the Chapter 5 error path and Chapter 6 retry policy are separate. wrap_tool_call can translate an exception into a message. ToolRetryMiddleware decides whether to call the tool again first.

Do not blindly retry side effects

Retrying a read is different from retrying a payment, email, or database write. Idempotency and service-level guarantees belong to the tool implementation and the external system.

Official source

The ToolRetryMiddleware docs define retry_on, exponential backoff, and the continue versus error failure behaviors.

Fallback, Routing, and Approval

Middleware can solve several different problems. Do not collapse them into one vague idea called “routing.”

NeedSmallest fitting policyWhat it actually decides
Primary model failedModelFallbackMiddlewareTry ordered fallback models after failure.
Model depends on request statewrap_model_callChoose or replace the model before this call.
Many tools existLLMToolSelectorMiddlewareUse a selector model to reduce the visible tool set.
High-impact tool needs approvalHumanInTheLoopMiddlewarePause before execution and resume after a decision.

These policies have different costs. Fallback is failure-only, not latency-based routing. Tool selection adds another model call. Human approval requires a checkpointer and stable thread ID so the run can resume.

When to customize

Configure the standard agent first. Add middleware when the topology is still a normal model-tools loop with extra policy. Move to raw LangGraph when you need deterministic branches, parallel work, or several agent calls stitched together.

The Bounded Order Assistant

Put the pieces together. This lab stays provider-neutral and uses the Chapter 5 in-memory tools. It does not call a real database or perform a destructive action.

from langchain.agents import create_agent
from langchain.agents.middleware import (
    ModelCallLimitMiddleware,
    ToolRetryMiddleware,
)

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[lookup_order, get_account_tier],
    system_prompt=(
        "You are a concise order assistant. "
        "Use tools for facts; never invent an order status."
    ),
    middleware=[
        safety_gate,
        ModelCallLimitMiddleware(run_limit=3, exit_behavior="end"),
        ToolRetryMiddleware(
            tools=["lookup_order"],
            max_retries=2,
            retry_on=(TimeoutError,),
            on_failure="continue",
        ),
    ],
)

result = agent.invoke({
    "messages": [{
        "role": "user",
        "content": "Check ORD-1042 and tell me my account tier.",
    }],
})
Predict before running

For a normal request, the gate allows the run. The model can call the tools, but no invocation can make more than three model calls. A TimeoutError from lookup_order can be retried twice; an exhausted retry becomes a ToolMessage because the policy says continue.

Now change the request to: Delete ORD-1042. The deterministic gate returns an assistant message and jumps to end. The model never receives the request.

The durable boundary

The model proposes. Tools act. The harness limits, checks, retries, routes, or pauses. LangGraph becomes the next tool when the overall topology needs explicit nodes and edges.
