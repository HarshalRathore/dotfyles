Agent Harnesses

Chapter 6 quick reference. create_agent parameters, middleware hooks, guardrails, limits, retries, routing, and the customization ladder.

The mental model

An agent is a model calling tools in a loop. The harness is the policy layer around that loop. create_agent is LangChain's configurable harness. Middleware adds policy at the seams without rebuilding the loop. LangGraph opens the loop into explicit nodes and edges when the topology changes.

Provider-neutral

All examples use provider-neutral model identifiers (openai:gpt-5.5). The harness, middleware, and guardrail patterns work identically across providers. No example depends on provider-specific features.

1. create_agent core parameters

Start with these four controls. They shape the harness and nothing else.

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[lookup_order, get_account_tier],
    system_prompt="Use tools for order facts.",
    middleware=[...],
)
ParameterUse it forDo not confuse it with
modelA provider-neutral model string or model instance.The harness itself.
toolsThe callable actions whose schemas the model can see.Runtime context hidden from the model.
system_promptStable role and operating instructions.Authorization or a hard stop.
middlewareChecks and policies around execution.A replacement for the agent loop.

Note A system prompt is model guidance, not authorization. If a rule must hold even when the model ignores instructions, enforce it in deterministic Python middleware or tool code. Provider implementations interpret system prompts differently; do not rely on them as a security boundary.

Other parameters are available but secondary to the harness layer: response_format shapes the final agent output, context_schema types per-run context, and checkpointer persists thread state.

2. Middleware hooks

Middleware runs inside the compiled LangGraph that create_agent returns. There are two hook styles.

Node-style
before_agent
before_model
after_model
after_agent
Run at named points. Return state updates or short-circuit a run. before_agent and after_agent run once per invocation; model hooks run per model iteration.
Wrap-style
wrap_model_call
wrap_tool_call
Surround one model or tool call. Decide whether the handler runs zero, one, or multiple times. Useful for retries, transformation, and interception.
NeedWhich hookRuns
Check once at the startbefore_agentOnce per invocation
Inspect every model responseafter_modelAfter each model call
Retry a failing tool callwrap_tool_call or built-in retryZero or more times per call
Intercept or transform a tool resultwrap_tool_callOnce per tool call
Replace the model per requestwrap_model_callBefore each model call
Run cleanup after the invocationafter_agentOnce per invocation

Reminder before_model and after_model repeat when the agent loops — they are not one-time setup hooks. If the agent makes three model calls, each runs three times.

3. Deterministic before_agent guardrail

A guardrail prevents the model from seeing unsafe input. The simplest useful guardrail runs before the model sees the request, applies keyword rules in Python, and short-circuits to the end when triggered.

from typing import Any
from langchain.agents.middleware import AgentState, before_agent
from langgraph.runtime import Runtime

BLOCKED_WORDS = {"delete", "transfer"}

@before_agent(can_jump_to=["end"])
def safety_gate(
    state: AgentState,
    runtime: Runtime,
) -> dict[str, Any] | None:
    if not state["messages"]:
        return None

    first_message = state["messages"][0]
    if first_message.type != "human":
        return None

    if any(word in first_message.content.lower() for word in BLOCKED_WORDS):
        return {
            "messages": [{
                "role": "assistant",
                "content": "This assistant cannot perform that operation.",
            }],
            "jump_to": "end",
        }
    return None
PatternWhat it does
@before_agent(can_jump_to=["end"])Register a node-style hook that may short-circuit before the model runs.
return {"jump_to": "end", "messages": [...]}Inject a terminal message and skip the rest of the graph.
return NoneAllow the run to proceed unmodified.
Teaching example, not production security

Keyword checks miss paraphrases, encoded input, and every other bypass. Authorization and dangerous side-effect controls must live at the tool or service boundary, not in pattern-matching middleware.

4. ModelCallLimitMiddleware

A model can make reasonable decisions and still use too many calls. The harness needs a budget.

from langchain.agents.middleware import ModelCallLimitMiddleware

agent = create_agent(
    model="openai:gpt-5.5",
    tools=tools,
    middleware=[
        safety_gate,
        ModelCallLimitMiddleware(
            run_limit=3,
            exit_behavior="end",
        ),
    ],
)
LimitProtectsScope
run_limitOne invocation from making too many model calls.Resets on the next invocation.
thread_limitA persistent conversation from accumulating too many calls.Requires a checkpointer.
ToolCallLimitMiddlewareExpensive or risky tool execution.Global or one named tool.

exit_behavior="end" stops gracefully when the limit is reached. exit_behavior="error" raises instead. Pick based on whether the caller needs a normal terminal state or an explicit failure signal.

Cost control is behavior control

Limits are not only billing protection. They make the agent's possible execution finite, which makes testing and incident analysis tractable.

5. ToolRetryMiddleware

Retries are a policy, not a guarantee that a request is valid. A timeout may be transient. An unknown order ID is usually permanent bad input.

from langchain.agents.middleware import ToolRetryMiddleware

agent = create_agent(
    model="openai:gpt-5.5",
    tools=[lookup_order],
    middleware=[
        ToolRetryMiddleware(
            tools=["lookup_order"],
            max_retries=2,
            retry_on=(TimeoutError,),
            on_failure="continue",
        ),
    ],
)
PolicyResult after retries are exhausted
on_failure="continue"Return a ToolMessage error so the model can respond.
on_failure="error"Re-raise the exception and stop the agent execution.
retry_on=(TimeoutError,)Retry only the failure type you consider transient. Omit to retry any exception.
Do not blindly retry side effects

Retrying a read is different from retrying a payment, email, or database write. Idempotency and service-level guarantees belong to the tool implementation and the external system.

6. Fallback, routing, and approval

Middleware can solve several different routing problems. Do not collapse them into one vague idea.

NeedSmallest fitting policyWhat it actually decides
Primary model failedModelFallbackMiddlewareTry ordered fallback models after failure.
Model depends on request statewrap_model_callChoose or replace the model before this call.
Many tools existLLMToolSelectorMiddlewareUse a selector model to reduce the visible tool set.
High-impact tool needs approvalHumanInTheLoopMiddlewarePause before execution and resume after a decision.

These policies have different costs. Fallback is failure-only, not latency-based routing. Tool selection adds another model call. Human approval requires a checkpointer and stable thread ID so the run can resume.

7. The customization ladder

Three tiers of increasing power. Start as high on the ladder as the topology demands.

LevelDetailsWhen to use
1. ConfigureSet model, tools, and system_prompt on create_agent.A standard model-tools loop with a static prompt.
2. MiddlewareAdd guardrails, limits, retries, fallbacks, routing, or approval hooks.The topology is still a model-tools loop with extra policy.
3. LangGraphWrite explicit nodes, edges, conditional branches, parallel work, and multiple agent calls.The topology changes: branching, parallelism, or several agent calls stitched together.

Rule of thumb Configure first. Add middleware when checks and limits are needed. Move to LangGraph when "model plus tools plus loop" is no longer enough to describe the workflow.

8. Checklist

  • Every harness starts with a model, tool list, system prompt, and middleware array.
  • Use before_agent for checks that must run before the model sees the request.
  • Use wrap-style hooks (wrap_model_call, wrap_tool_call) for retries, transformation, and interception.
  • Set a model-call limit to bound each invocation's cost and behavior.
  • Configure tool retries with retry_on for transient failures and on_failure for exhausted retries.
  • Route, fall back, select tools, or request approval when the policy requires it — do not collapse these into one middleware.
  • A system prompt is model guidance. Middleware is application control.
  • Configure first, add middleware second, move to LangGraph when the topology changes.
