Glossary: LangChain & LangGraph

Every term used in this course, defined in plain language. Back to Lesson 1 · Course Index

ABCDEGHILMNPRSTW

A

args_schema
The input schema attached to a tool. LangChain can infer it from a function's type hints, or you can provide a Pydantic model or JSON Schema explicitly with @tool(args_schema=...). The schema tells the model which arguments it may construct. [Source]
agent
A model that calls tools in a loop until a task is complete. In LangChain, agents are built with create_agent, which bundles a model, a set of tools, and a system prompt. The agent receives a message, decides which tool to call (or whether to answer directly), calls it, and loops. The best mental model: agent = model + tools + loop. [Source]
AIMessage
The message type for model responses. Returned by chat models when you invoke them. Contains the model's reply text in .content, and may carry tool_calls when the model decides to invoke a tool. See messages for all types. [Source]
after_agent
A node-style middleware hook that runs once after the agent completes its execution loop. Receives the agent state and runtime; returns an optional dict of state updates. Useful for teardown, logging, metrics collection, and final output validation. [Source]
after_model
A node-style middleware hook that runs after each model response. Receives the agent state (including the model's output) and runtime; returns an optional dict of state updates. Useful for logging model responses, response validation, post-processing, and state tracking. [Source]

B

before_agent
A node-style middleware hook that runs once before the agent starts processing an invocation. Receives the agent state and runtime; returns an optional dict of state updates. Use for early validation, input transformation, guardrails, and dynamic prompt injection. Can jump to a different graph node via can_jump_to. [Source]
before_model
A node-style middleware hook that runs before each model call. Receives the agent state and runtime; returns an optional dict of state updates. Use for policy enforcement, guardrails, dynamic system prompt injection, and input filtering before the model sees it. Can jump to a different graph node via can_jump_to. [Source]

C

chat model
The LangChain abstraction for an LLM that accepts a list of messages and returns an AIMessage. Every provider (OpenAI, Anthropic, Ollama, etc.) is wrapped into this same interface so your code works the same way regardless of backend. Instantiated via init_chat_model() or through provider-specific constructors. [Source]
checkpointer
A LangGraph component that persists a thread's graph state at each step as a checkpoint. Enables fault tolerance (resume from the last checkpoint after a crash), time travel (replay from any past checkpoint), and human-in-the-loop (interrupt execution and resume). Checkpointers are passed to graph.compile(checkpointer=...). [Source]
compile
The required final step before a LangGraph can be used. graph = graph.compile(...) runs structural checks (are all nodes reachable? are all edges defined?) and accepts runtime configuration like the checkpointer and breakpoints. A graph that hasn't been compiled will raise an error when you try to invoke it. [Source]
create_agent
The modern LangChain entrypoint for building agents. Replaces the deprecated LLMChain and AgentExecutor patterns. Takes a model string, a list of tools, and a system prompt, and returns a runnable agent. Created agents are built on LangGraph under the hood. [Source]

D

Deep Agents
A higher-level SDK built on LangGraph that provides batteries-included agent capabilities: planning, subagent spawning, filesystem access, automated context engineering. Not covered in this beginner course. Mentioned so you know it exists for when you outgrow raw LangChain or LangGraph. [Source]

E

edge
In LangGraph, a function that determines which node to execute next based on the current state. Edges can be fixed (always go from node A to node B) or conditional (inspect state and choose a different next node depending on the values). "Edges tell what to do next." [Source]

G

graph
The central object in LangGraph. A graph is a network of nodes (functions that do work) connected by edges (functions that route), with a shared state object flowing through all of them. Built with StateGraph(StateType), populated with add_node and add_edge, and made runnable with compile(). [Source]
guardrail
A middleware pattern that enforces constraints on agent behavior. Implemented via before_agent, before_model, or after_model hooks; a guardrail can block execution, inject safety instructions, filter inputs or outputs, or route to a different node (via can_jump_to). Examples: output content filtering, topic restrictions, PII detection, safety checks. [Source]

H

harness
Everything around the model loop: the prompt, the tool definitions, the middleware that shapes agent behavior. In LangChain, create_agent provides the default harness. You can customize it with middleware for guardrails, retries, routing, and human-in-the-loop. [Source]
HumanMessage
The message type representing user input. When a person sends a prompt to an agent, it becomes a HumanMessage in the message list. Usually the first message in any conversation turn. See messages for all types. [Source]

I

init_chat_model
The provider-neutral LangChain function for constructing a chat model. Import from langchain.chat_models and call with a provider:model string such as openai:gpt-5.5, anthropic:claude-sonnet-4-6, or ollama:llama3.1. Accepts standard parameters like temperature, max_tokens, timeout, and max_retries — though exact support varies by provider. Returns a BaseChatModel instance. [Source]

L

LangChain
The high-level Python framework for building LLM agents. Provides create_agent, model and tool abstractions, middleware, and standard agent patterns. Built on top of LangGraph. Every LangChain agent runs on a LangGraph runtime under the hood. You don't need to know LangGraph to use LangChain. [Source]
LangGraph
The low-level orchestration runtime for long-running, stateful agents. Inspired by Google's Pregel and Apache Beam. Provides durable execution, persistence (checkpointers), streaming, and human-in-the-loop. LangGraph can be used standalone with any model provider. It does not require LangChain. Its API is modeled after NetworkX. [Source]
LangSmith
LangChain Inc's paid SaaS platform for tracing, evaluation, and observability. Used to debug agent runs, compare model outputs, and monitor deployed agents. Not open source. Not covered in this beginner course. [Source]

M

max_retries
A standard parameter for chat model calls. Sets how many times the framework retries a model call when it fails due to a transient error (network hiccup, rate limit, server error). Passed to init_chat_model() or create_agent(). Default is 6 retries. [Source]
max_tokens
A standard parameter that caps the length of the model's response in tokens. Controls both cost and response size. Passed to init_chat_model() or create_agent(). Not every provider supports hard caps in the same way. [Source]
message
The core input/output unit in LangChain. Every interaction with a model is structured as typed messages. The main types are HumanMessage (user input), AIMessage (model response — may carry tool_calls), SystemMessage (instructions that set model behavior), and ToolMessage (tool results, correlated via tool_call_id). Messages carry a .content field and optional metadata like .response_metadata. [Source]
MessagesState
A prebuilt state type in LangGraph that includes a messages: list[AnyMessage] key with the add_messages reducer. New messages are appended to the list rather than replacing it. This is the standard pattern for conversation state. [Source]
middleware
Extensions that modify agent behavior by hooking into the compiled LangGraph that create_agent returns. Provides two hook styles: node-style hooks (before_agent, before_model, after_model, after_agent) that run sequentially at specific execution points, and wrap-style hooks (wrap_model_call, wrap_tool_call) that intercept and control each model or tool call. Examples: guardrails, retry logic, routing, human-in-the-loop. Passed to create_agent via the middleware= parameter. [Source]
model
The LLM reasoning engine used by agents. In LangChain, a model accepts messages and returns an AIMessage. Models support tool calling, structured output (returning validated JSON via Pydantic), multimodality (images, audio), and reasoning. Standard call parameters include temperature (response randomness), max_tokens (response length cap), timeout (per-request deadline), and max_retries (transient-failure retries). Provider packages like langchain-openai and langchain-anthropic wrap different backends into a common interface. [Source]
ModelCallLimitMiddleware
A built-in middleware that limits the number of model calls per thread or per invocation. Configured with thread_limit (max calls across all runs in a conversation thread) and run_limit (max calls per single invocation). exit_behavior controls what happens when the limit is reached: 'end' (graceful termination) or 'error' (raise an exception). Requires a checkpointer for thread limits. [Source]
ModelFallbackMiddleware
A built-in middleware that automatically falls back to alternative models when the primary model fails. Accepts one or more fallback model identifiers (or BaseChatModel instances). When the primary model call fails, the middleware tries each fallback in order. Useful for building resilient agents that handle model outages and provider failures. [Source]

N

node
In LangGraph, a function that receives the current state, performs computation, and returns a state update (or a diff to apply). "Nodes do the work." Each node focuses on one task: call an LLM, run a tool, validate output, transform data. Nodes are added to a graph with add_node(name, function). [Source]

P

provider package
A separate Python package that wraps a specific LLM provider into LangChain's model interface. Examples: langchain-openai, langchain-anthropic, langchain-google-genai, langchain-ollama, langchain-aws. These must be installed independently of langchain itself. [Source]

R

reducer
A function that specifies how to apply updates to each key in the graph state. By default, updates override the previous value. Common custom reducers: operator.add (for incrementing counters), add_messages (for appending messages to a list). Reducers are attached using Python's Annotated[type, reducer_fn] syntax. [Source]
response_format
An agent-level parameter on create_agent() that instructs the model to return structured output matching a Pydantic schema. Distinguish from with_structured_output(), which is the standalone model method. response_format configures the whole agent to respond in a structured shape. [Source]

S

state
The shared data structure that flows through every node and edge in a LangGraph graph. Defined as a TypedDict, dataclass, or Pydantic model. Each key in the state can have an associated reducer that controls how updates are applied. State is the graph's single source of truth. Nodes read from it, write diffs to it, and edges route based on it. [Source]
StateGraph
The main LangGraph class for building graphs. Parameterized by a user-defined State type. You create an instance, add nodes and edges, then compile it into a runnable object. StateGraph(MessagesState) is the most common starting point. [Source]
Store
LangGraph's long-term memory abstraction. A key-value document store organized by namespaces (hierarchical prefixes). Unlike checkpointers (which store thread-scoped state), the Store persists data across threads and conversations. Example: namespace ("users", user_id) with document {"preferences": ..., "history": ...}. [Source]
structured output
Returning model output as a validated Pydantic schema rather than free text. The model returns a JSON object matching a schema you define. Use model.with_structured_output(PydanticSchema) on a chat model to get parsed output directly, or pass response_format= to create_agent() for agent-level enforcement. Provider support and output consistency vary, so always validate results in production. [Source]
SystemMessage
The message type for system-level instructions that set the model's behavior. Placed at the start of the message list, a SystemMessage tells the model its role, constraints, and persona. Unlike HumanMessage or AIMessage, its content is instruction, not conversation. See messages for all types. [Source]
system_prompt
A parameter on create_agent() that sets the agent's system instructions. Accepts a string or SystemMessage. The system prompt tells the model its role, constraints, and persona. For dynamic prompts that change at runtime, use middleware hooks like before_agent or before_model. [Source]

T

temperature
A standard model parameter controlling response randomness. Lower values (near 0) produce more deterministic, focused outputs; higher values (near 1 or 2) produce more diverse, creative ones. Passed to init_chat_model() or create_agent(). The exact range and effect vary by provider. [Source]
thread
A conversation scope identified by a thread_id in the runtime config. Checkpoints are per-thread, so state from one thread is isolated from others. Threads enable multi-turn conversations and fault-tolerant long-running agents. [Source]
timeout
A standard parameter that sets a per-request deadline in seconds for model calls. If the provider doesn't respond within the timeout, the call raises an error. Passed to init_chat_model() or create_agent(). [Source]
tool
A callable function with well-defined inputs and outputs that an agent can invoke. Created with the @tool decorator in LangChain. Type hints define the input schema and the docstring becomes the default tool description. Tools can receive injected runtime data through ToolRuntime: state, context, store, stream writer, execution info, config, and tool-call ID. [Source]
ToolMessage
The message type for returning tool execution results to the model. Created by the agent harness after a tool runs. The tool_call_id field correlates it to the specific AIMessage tool call that triggered it. See messages for all types. [Source]
tool_call_id
The correlation ID shared by an AIMessage tool call and its resulting ToolMessage. It lets the model match each tool result to the request that produced it, including when several tools run in one turn. [Source]
ToolRuntime
An injected parameter type that gives a tool access to execution context without exposing that parameter in the model-visible schema. Its fields include state (short-term conversation data), context (immutable per-run data), store (long-term data), stream_writer, execution information, config, and tool_call_id. [Source]
ToolRetryMiddleware
A built-in middleware that automatically retries failed tool calls with exponential backoff. Configurable with max_retries, backoff_factor, initial_delay, max_delay, and jitter (±25% random delay to avoid thundering herd). on_failure controls behavior when retries are exhausted: 'continue' (return error to the model), 'error' (re-raise exception), or a custom function. retry_on filters which exception types trigger a retry. [Source]
wrap_tool_call
An agent middleware decorator for intercepting tool execution. It can catch an exception and return a custom ToolMessage so the model receives an error result instead of the run stopping immediately. [Source]

W

with_structured_output
A method on BaseChatModel that wraps a model to return parsed Pydantic output. Call model.with_structured_output(MyPydanticSchema) to get a model that returns validated schema objects instead of raw AIMessage instances. The agent-level equivalent is response_format= on create_agent(). [Source]
